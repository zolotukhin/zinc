The [single-slot consistency fix](../ROCM_SINGLE_SLOT_CORRECTNESS.md) clears the
known ROCm MoE continuation and dense-model request-reuse blockers. The latest
[bounded Gemma prefill follow-up](../ROCM_GEMMA_BOUNDED_PREFILL.md) also avoids
serial fallback when smaller scratch fits. Gemma 31B now completes the three
core OpenCode fixtures at 8K with an explicit 600-second fixture budget; its
shorter 300-second trial remains failed. [OpenCode validation](../OPENCODE_RELEASE_VALIDATION.md)
records the individual executables, budgets and remaining limits. Final
candidate qualification remains pending.

The [reference audit](../RDNA4_REFERENCE_VALIDATION.md) corrects the earlier HIP
revision claim: its recorded executable reports an older revision than the
intended checkout. Historical results retain their exact reference hashes and
diagnostic scope. Fresh worker runs must verify native reference backends and
unchanged executable/library identities, alongside the current cancellation
and EOS checks.

## Current status

Preview `c1d2b7b4` passes all three CPU packaging jobs and normal CI,
including all four Linux optimization modes and the macOS build/test job.
Metal, Vulkan and ROCm archives pass dependency/ABI audits and installation
from an extracted archive outside the checkout.

That exact preview passes both complete R9700 worker matrices:
[Vulkan run 41273720545](https://github.com/zolotukhin/zinc/actions/runs/41273720545)
has 288/288 exact reference choices;
[ROCm run 41273692821](https://github.com/zolotukhin/zinc/actions/runs/41273692821)
has 287/288 exact choices and one policy-qualified near-tie. Each exercises six
pinned models, 72 tokenizer cases and 54 complete HTTP reference replays across
initial requests, real chat-stream cancellation and context/error recovery.
ROCm Gemma 31B also passes 48 forced-small-chunk choices. The separate EOS probe
passes 12 raw/JSON-chat/SSE cases before, at and after the EOS token boundary on
the [earlier preview](/zinc/validation/worker-readiness-2026-11-01.json).
The [latest portable evidence](/zinc/validation/worker-readiness-c1d2b7b4-2026-11-01.json)
records exact archives, references, model pins and cleanup. These are unsigned
preview checks, not signed-candidate qualification.

Intel's earlier `dbbfff54` Vulkan archive passes 84 kernel cases and four model
rows: the starter, 35B MoE, 27B dense and 9B dense. Its 191/192 exact choices plus
one qualified near-tie meet the unchanged policy. This includes the Unicode
case that exposed the 27B prefill bug: the tiled/grouped attention kernels
assume 64-lane subgroups, while the tested Xe2 driver supports only 16/32.
Dispatch now uses generic batched attention when 64 lanes are unavailable,
preserving the other accelerated prefill stages. A separate `f1ef2aa9` archive
also passes Gemma 31B: 48/48 exact choices, tokenizer/API checks and 84 kernel
cases, using `c1d2b7b4` validation helpers and pinned native reference libraries.
Its report records both sources; it does not combine different archives into a
six-model pass. Gemma 26B is still downloading, and an isolated registered
worker is still needed. A complete Intel matrix on one archive remains pending.

The [original bring-up evidence](/zinc/validation/worker-bringup-2026-10-31.json)
retains earlier failures and the attention isolation controls. Raw completions
now omit EOG markers and report normal token limits as `length`; EOS wins when
it lands exactly on the limit. Cancellation checks require real chat SSE
content before disconnecting, then replay complete reference continuations.

Earlier coding and performance reports retain their recorded executables,
budgets and limits. The [reference provenance audit](https://github.com/zolotukhin/zinc/pull/41)
corrects an older HIP reference-revision claim; those comparisons remain
exact-byte diagnostics. The fresh worker references are independently pinned.
[OpenCode validation](../OPENCODE_RELEASE_VALIDATION.md) retains the separate
8K coding results and Gemma's explicit 600-second fixture budget. None of these
checks qualifies optional KV/context/concurrency settings or other binaries.

There is no published binary release. The dedicated non-root RDNA4 worker has
seven verified model mounts and pinned Vulkan/HIP references; both profiles
share one reservation. Its loader cache supports the staged driver/runtime
without inherited library overrides. Readiness reports cannot certify a release
candidate. Seven worker roles and Apple signing remain unprovisioned, and all
nine profiles still need qualification on the final signed candidate.

The [maintainer configuration preflight](../RELEASING.md#check-configuration-before-dispatch)
reports missing assignments, offline/unmatched workers, signing secret names
and environment protections without exposing private runner details. Its
optional dispatch mode launches a candidate only when these checks pass;
configuration readiness still requires the complete candidate qualification.

The small starter is still experimental. Keep all nine required profiles for
the first stable release; missing hardware is not a reason to skip a profile.

## Distribution contract

The [release policy](https://github.com/zolotukhin/zinc/blob/main/config/release/targets.json)
is the source of truth for targets, OS/ABI floors, hardware profiles, model
hashes, context limits, and the reference engine revision.

| Archive suffix        | Runtime baseline                                     | Required hardware profiles          |
| --------------------- | ---------------------------------------------------- | ----------------------------------- |
| `macos-aarch64-metal` | macOS 15+, native ARM64; signed and notarized        | Apple7, Apple8, Apple9, Apple10     |
| `linux-x86_64-vulkan` | glibc 2.35+, Vulkan 1.3 driver                       | RDNA3, RDNA4, Strix Halo, Intel Xe2 |
| `linux-x86_64-rocm`   | glibc 2.39+, ROCm 7.2.4 and runtime compiler headers | RDNA4 `gfx1201`                     |

Metal and Vulkan include browser chat. ROCm provides CLI/HTTP chat without the
built-in UI or hot model switching. CUDA remains experimental and source-only.
Models and GPU drivers are separate installations.

Required hardware that is unavailable blocks that support claim. Changing the
launch matrix is an explicit policy change; an omitted or skipped profile does
not count as a pass. Historical source-build benchmarks and OpenCode trials
remain useful evidence, but cannot certify a different packaged executable.

## Implemented

- Frozen source SHA/version and baseline CPU/OS targets for all three archives.
- Complete shader inventories, dependency/ABI audits, normalized archive metadata,
  per-file checksums, and executable identity probes.
- Verified user-local installation, atomic activation, backend selection, safe
  reinstall, failure handling, and rollback without moving models.
- Separate untrusted packaging, trusted candidate, signing, hardware validation,
  provenance, protected promotion, and public-install workflows.
- Packaged-byte GPU/model/API/reference checks, process cleanup, generated
  validation tables, and resumable publication that refuses replacement bytes.

See [release engineering](https://zolotukhin.ai/zinc/docs/releasing/) for the
maintained commands and configuration, and [binary installation](https://zolotukhin.ai/zinc/docs/binary-releases/)
for the user-facing contract. This readiness note replaces the original design
proposal; implementation details belong in those guides and the policy.

## Remaining launch gates

1. Finish configuring the eight runner roles covering nine hardware profiles. Reserve
   shared GPUs and install each worker's private model/reference configuration.
2. Configure Developer ID signing/notarization credentials in `release-signing`.
   The main-branch restrictions and required publication reviewer are configured.
3. Run an RC from one frozen SHA. Review all packaged-artifact reports, exact
   model hashes, correctness/API checks, and process cleanup.
4. Qualify and promote the small starter in the catalog from real hardware
   evidence. Keep optional KV/MTP/context/concurrency claims within their tested
   scope; review performance regressions separately.
5. Rehearse failed validation, unavailable workers, interrupted upload, duplicate
   versions, and rollback. CPU contracts cover these failure paths, including an
   accepted upload whose reply is lost and a subsequent write-free retry. The
   actual signed-RC publication/public-install rehearsal remains pending. Build
   a new final-version candidate after source changes.
6. Publish the approved candidate unchanged. Verify public downloads and clean
   installation before closing issue #10.

No release tag or public archive should be created from the packaging preview.
