# ZINC 0.1.0 release plan

Status: release automation implemented in [PR 33](https://github.com/zolotukhin/zinc/pull/33); infrastructure and hardware qualification pending.

Target: `v0.1.0`. Tracking: [issue 10](https://github.com/zolotukhin/zinc/issues/10).

Audit baseline: `d1300eb1`, 2026-10-26

Ship downloadable, installable **Metal, Vulkan, and ROCm** builds. Keep CUDA experimental and available from source. Build each candidate once, validate the packaged bytes on the supported hardware, and publish those same bytes after one release approval.

The first release promises working local text inference and a documented subset of the OpenAI-compatible API on an explicit hardware/model matrix. Metal/Vulkan include the built-in browser chat; ROCm's standalone server provides CLI/HTTP chat without that UI or hot model switching. A successful compiler job alone does not certify GPU inference.

Implementation reference: [release engineering](https://zolotukhin.ai/zinc/docs/releasing/), [binary installation](https://zolotukhin.ai/zinc/docs/binary-releases/), and the [machine-readable policy](https://github.com/zolotukhin/zinc/blob/main/config/release/targets.json). The initial implementation supplies all three builds, safe installation/rollback, artifact-based GPU/API gates, notarization/provenance and protected promotion. It creates no public release by itself. The starter remains experimental until real GPU evidence is reviewed; stable publication rejects that state. Optional-feature, memory-rejection and performance qualification remain part of release readiness.

## 1. Platforms and chips

### Binary targets

| Platform and backend | Proposed release support                                                                    | Hardware evidence required                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| macOS ARM64, Metal   | Apple Silicon M1 through M5, including each family's available Pro, Max, and Ultra variants | Release tests covering Apple7, Apple8, Apple9, and Apple10 GPU families                                |
| Linux x86_64, Vulkan | AMD RDNA3, RDNA4 discrete GPUs, and Strix Halo; Intel Arc Xe2/Battlemage                    | Separate tests for RDNA3, RDNA4, the APU, and Intel's subgroup behavior                                |
| Linux x86_64, ROCm   | RDNA4 `gfx1201`, initially the Radeon AI PRO R9700 and compatible RX 9070-family devices    | Packaged ROCm build on the validated `gfx1201` stack; document the actual tested board and memory size |

One Metal archive serves all supported Apple chips. One Vulkan archive serves both AMD and Intel GPUs. Linux binaries run on both AMD and Intel x86_64 CPUs; CPU vendor does not select the GPU backend. ROCm is a separate binary because its libraries, runtime compiler, and validation requirements differ.

CUDA on RTX 4090/5090 remains an experimental source build. Linux ARM64, Intel Macs, native Windows, stable WSL support, older AMD GPUs, Intel Arc Alchemist, and ZINC_RT binaries are outside the 0.1.0 download matrix. Broader compatibility can be investigated without adding a release support promise.

### Chip coverage

| Family            | Chips and examples                           | Release treatment                                                                                                                       |
| ----------------- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Apple7            | M1 family                                    | Required Metal baseline, including a machine on the minimum supported macOS                                                             |
| Apple8            | M2 family                                    | Required Metal family check                                                                                                             |
| Apple9            | M3 and M4 families                           | Required family check; publish the exact tested models rather than implying every SKU was tested                                        |
| Apple10           | M5 family                                    | Required family check; ordinary Metal kernels remain the baseline, with no TensorOps dependency                                         |
| AMD RDNA3         | `gfx1100`, such as RX 7900 XT/XTX            | Required Vulkan representative; other RDNA3 SKUs remain compatible targets with their own memory limits                                 |
| AMD RDNA4 Navi 48 | `gfx1201`, such as R9700 and RX 9070/9070 XT | Required Vulkan and ROCm representative; serialize tests using the same physical GPU                                                    |
| AMD RDNA4 Navi 44 | `gfx1200`, such as RX 9060-class cards       | Compatibility target until a packaged-artifact run is recorded; do not infer certification from Navi 48                                 |
| AMD Strix Halo    | `gfx1151`, Radeon 8050S/8060S                | Required APU Vulkan check, including shared-memory limits and unified-memory behavior                                                   |
| Intel Arc Xe2     | B570/B580 and Arc Pro B-series               | Required Intel Vulkan check; use a large-memory G31-class device for large-model coverage and a smaller-memory profile for fit behavior |

Strix Halo is **RDNA 3.5**, not RDNA4. The hardware guide now uses that terminology. AMD documents the architecture in its [Strix Halo guide](https://rocm.docs.amd.com/en/docs-7.2.0/how-to/system-optimization/strixhalo.html).

Apple's [Metal feature tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf) map M1 to Apple7, M2 to Apple8, M3/M4 to Apple9, and M5 to Apple10. Keep runtime capability detection rather than producing separate chip-specific downloads.

These are release targets, not completed certifications. A published support table must distinguish **tested board**, **supported family**, and **compatible but unverified**. Missing required hardware blocks the corresponding support claim; a skipped test does not count as a pass. If capacity is unavailable, explicitly reduce the launch matrix before publishing.

### OS and ABI contract

| Artifact | Proposed baseline                                              | Required proof before freezing the release                                                                                                                 |
| -------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Metal    | macOS 15+, ARM64 with M1-compatible CPU instructions           | Explicit deployment target; packaged execution on macOS 15 and a current macOS. Newer Mac models also require their own factory minimum OS                 |
| Vulkan   | glibc 2.35+, baseline x86_64 instructions                      | Build against the chosen baseline; inspect ELF dependencies and symbol versions; install/execute on clean Ubuntu 22.04/24.04 and Debian 12/13 environments |
| ROCm     | Ubuntu 24.04 reference environment, ROCm 7.2.4 reference stack | Record the actual glibc floor and library SONAMEs; test on the documented matching driver/userspace stack                                                  |

These minimums are proposed compatibility targets. Confirm them with the actual release artifact before advertising them. A container verifies userspace compatibility, not an older kernel or physical GPU driver. The kernel/driver needed by a particular GPU remains a separate requirement.

Use explicit target/CPU options rather than the builder's native CPU. Pin the macOS deployment target and verify it in the Mach-O load commands. Verify the Linux ABI with `readelf`/`objdump`; do not assume that `ubuntu-latest` produces a portable binary. Alpine/musl and raw standalone binaries on NixOS are not certified by the glibc matrix; the existing Nix build remains a separate installation path.

Vulkan users need a working Vulkan loader and GPU driver, including the features actually used by the selected pipelines. Compiled SPIR-V ships in the archive; end users should not need Zig, Bun, or `glslc`. Metal users should not need a development checkout or Xcode to run the binary; verify that on a clean Mac.

ROCm needs more than the GPU driver: `amdhip64`, `hiprtc`, `hipblas`, and compatible HIP/rocWMMA headers used by runtime compilation. `rocm_shim.c` passes the ROCm include directory to hipRTC, and the embedded kernel source includes HIP and rocWMMA headers. Document and test the minimal package set, including a relocated `ROCM_PATH`; do not describe a runtime-libraries-only installation as sufficient.

## 2. Download and install contract

Publish three primary archives:

| Asset                                    | Contents                                                                                               |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `zinc-v0.1.0-macos-aarch64-metal.tar.gz` | ARM64 executable, Metal shader sources, metadata, README, license                                      |
| `zinc-v0.1.0-linux-x86_64-vulkan.tar.gz` | Portable x86_64 executable, compiled SPIR-V, metadata, README, license                                 |
| `zinc-v0.1.0-linux-x86_64-rocm.tar.gz`   | x86_64 executable with embedded kernel source, ROCm dependency instructions, metadata, README, license |

Also publish `SHA256SUMS.txt`, `release-manifest.json`, `validation.json`, provenance attestations, and a dependency/license inventory. Keep symbols as downloadable CI artifacts initially; public symbol archives are a useful P1 addition. Models and GPU drivers are not bundled.

The explicit backend suffixes are a proposed change from the current two archive names. Update the packager, installer, tests, documentation, and website together before the first release. No published binary releases currently need a compatibility alias.

`VERSION.json` identifies the version, full source SHA, target, backend, optimization mode, CPU baseline, and minimum OS/ABI. The combined release manifest binds every filename and SHA256 to that version/SHA, the pinned toolchain/build image, and the applicable validation results. Hardware records identify public GPU model/family and driver versions, excluding private machine identifiers.

### Installer behavior

Keep a user-local install with versioned directories and a stable `zinc` symlink. macOS selects Metal; Linux defaults to Vulkan. An explicit backend option such as `ZINC_BACKEND=rocm` selects ROCm. Never switch an existing installation's backend silently.

Before replacing `current`, the installer must:

1. Check OS, architecture, minimum OS/libc, and backend prerequisites. Preserve clear Rosetta and unsupported-platform errors.
2. Download a named version or resolve the latest stable release. Pre-releases require an explicit version/channel.
3. Verify the requested archive against its checksum and manifest. Reject a wrong target/backend/version, duplicate or absent checksum records, and unsafe archive paths or symlink escapes.
4. Extract into staging on the installation filesystem. Validate the complete runtime asset set and require `zinc --version` to succeed there.
5. Atomically switch the active symlink. Preserve the preceding installation and model cache for rollback.

The current installer suppresses failure from its final version probe. Replace that with a failing pre-activation check so an incompatible binary cannot be reported as successfully installed. Cover failed downloads, corrupt/truncated archives, missing dependencies, interrupted reinstall, spaces in paths, upgrade, backend switching, and rollback. Require no `sudo` for the ZINC files.

Checksums detect corruption. GitHub HTTPS distribution and independently verifiable build attestations establish the publishing path; do not describe an unsigned checksum downloaded beside an archive as an independent signature.

### macOS distribution

The proposed stable-release bar is Developer ID signing with hardened runtime, a secure timestamp, and successful Apple notarization. Supply signing credentials through a protected signing job and verify the quarantined download on a clean Mac. Do not make recursive quarantine removal the normal installation instructions.

For the tar archive, submit an Apple-supported ZIP envelope containing the same signed executable and validate Gatekeeper's online ticket lookup. A standalone CLI/tar archive cannot receive a stapled ticket like a supported installer or disk image; if offline Gatekeeper operation is required, add a signed/notarized PKG or DMG and validate that delivery path. Apple's [notarization guide](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) and [custom workflow guide](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow) govern the implementation.

Signing/notarization must finish before the archive digest is frozen and before GPU validation of the delivered executable. An unsigned development candidate remains a development candidate, rather than silently becoming the stable Mac download.

## 3. Existing infrastructure and concrete gaps

| Area                | Current implementation                                                                                              | Work remaining for 0.1.0                                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Version identity    | `build.zig` options and CPU-only `--version` exist                                                                  | Enforce consistent version/full SHA/target metadata across all artifacts                                                      |
| Runtime assets      | `src/runtime_assets.zig` supports an override and executable-relative lookup; build installs Vulkan/Metal assets    | Test extracted packages from a different working directory with source checkout unavailable                                   |
| Packaging           | `scripts/package_release.sh` packages Vulkan and Metal and writes `VERSION.json`                                    | Add ROCm, explicit backend names, dependency/ABI checks, normalized metadata, and package tests                               |
| Installer           | `scripts/install.sh` downloads two target archives, verifies SHA256, and installs symlinks                          | Three-backend selection, atomic activation, strict pre-activation execution, compatibility checks, rollback and failure tests |
| GitHub release jobs | `.github/workflows/release.yml` validates, builds Linux Vulkan/macOS Metal, generates checksums and a draft release | ROCm build, exact SHA pinning, artifact validation, signing, GPU jobs, provenance, and controlled promotion                   |
| Toolchains          | Zig and Bun pins exist                                                                                              | Read both pins in release jobs; release currently requests Bun `latest` and uses moving runner environments                   |
| GPU automation      | No repository self-hosted runners registered at audit time                                                          | Provision trusted hardware pools or an equivalent controlled job service before promising automatic hardware gates            |
| Managed models      | Six entries; two have SHA256 values                                                                                 | Fill the four empty hashes or withdraw those entries from release recommendations; pin upstream revisions and licenses        |
| Release docs        | Existing notes are a template with TBD validation rows                                                              | Generate actual supported combinations and limitations from the candidate results                                             |

Keep the existing scripts and workflow as the implementation foundation. Replace the stale checklist of already-implemented features with acceptance tests for their packaged behavior.

The current workflow also re-resolves a supplied ref independently in each job, accepts any `v*` string, and does not verify the final packaged artifacts on GPUs. Resolve one full commit SHA first, validate SemVer and ref identity, and pass immutable outputs to every downstream job. Pass dispatch inputs through environment variables and validate them before shell use.

For SDK setup, pin only the shader compiler, headers, and loader components actually needed. Avoid downloading a full GUI-heavy Vulkan SDK independently in every matrix job. Use bounded network timeouts, a pinned build image, and shared toolchain caching to keep package-download stalls from dominating release jobs.

## 4. Automatic jobs

### Triggers and cadence

| Event                      | Jobs                                                                                      | Outcome                                                                   |
| -------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Every PR                   | Existing CPU tests/build matrix, shader compilation, installer/package tests, site checks | Fast feedback without access to private GPU or signing workers            |
| Trusted `main`, nightly    | Representative GPU/model correctness and API tests; candidate package smoke               | Fresh evidence and regression detection for each available backend/family |
| Weekly                     | Full catalog/model/context matrix on sufficiently large devices; performance comparison   | Broader compatibility and performance history                             |
| Release candidate dispatch | All three signed/packaged artifacts, complete required hardware matrix, aggregate report  | A downloadable immutable candidate for review                             |
| Approved promotion         | Verify the candidate, create the final tag/release, upload and verify assets, publish     | Public release of the already-tested bytes                                |
| After publication          | Independent download/install/identity smoke                                               | Detect broken publication or installer links                              |

Reuse CI/reusable workflows rather than maintaining different release and PR build commands. Version selection is explicit for 0.1.0. Use SemVer and a release-preparation PR for version, notes, support manifest, and changelog. Build on the existing GitHub Actions workflow for the first release; adopt commit-based version automation after agreeing a commit/release policy.

### Candidate job graph

```text
resolve_candidate(version, source SHA, support policy)
  -> validate_source_and_tests
  -> build_metal / build_vulkan / build_rocm
  -> sign_and_notarize_metal
  -> package_and_freeze_digests
  -> verify_archives_and_installers
  -> gpu_metal[Apple7, Apple8, Apple9, Apple10]
     gpu_vulkan[RDNA3, RDNA4, Strix Halo, Intel Xe2]
     gpu_rocm[gfx1201]
  -> aggregate_required_results
  -> candidate_notes_and_downloads
  -> protected_publish_approval
  -> publish_same_artifacts
  -> verify_public_downloads
```

The GPU branches run in parallel where physical devices permit. The two AMD backends share a device reservation where they use the same card. Certification depends on successful required jobs and independently rejects missing, failed, stale or duplicate reports. A failed hardware job prevents certification from running; an unavailable runner or skipped check cannot yield a publishable candidate.

Run `post_publish` as a dependent job or dispatch it explicitly. Events created with `GITHUB_TOKEN` generally do not trigger another workflow, so a tag/release event alone cannot guarantee the publication check. See GitHub's [workflow token behavior](https://docs.github.com/en/actions/concepts/security/github_token).

| Job                 | Execution environment                 | Required evidence                                                                                        |
| ------------------- | ------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `resolve_candidate` | Hosted Linux                          | Valid SemVer, trusted workflow/source, full SHA on protected main, exact target/model policy             |
| `validate_source`   | Hosted CPU runners                    | Required unit/build/site checks, pinned Zig/Bun, clean source identity                                   |
| `build_vulkan`      | Pinned Linux build image              | Explicit target/CPU, compiled SPIR-V, symbol/dependency audit                                            |
| `build_rocm`        | Pinned ROCm development image         | HIP/hipRTC/hipBLAS ABI and needed header versions; embedded kernel source                                |
| `build_metal`       | Pinned hosted macOS/Xcode environment | ARM64/deployment-target checks and complete Metal assets                                                 |
| `sign_metal`        | Protected signing environment         | Developer ID verification, notarization receipt, final signed executable                                 |
| `verify_packages`   | Clean minimum/current userspaces      | Archive layout, manifest/digest consistency, symlink installation and successful CPU-only version output |
| `gpu_*`             | Explicit GPU-capable workers          | Packaged-artifact identity, actual hardware, model SHA, correctness/API/memory results                   |
| `attest_and_report` | Trusted hosted worker                 | Provenance, checksums, dependency inventory, validation report and readable summary                      |
| `publish`           | Protected release environment         | The exact approved candidate run and digests; tag/source identity; no rebuild                            |
| `post_publish`      | Clean hosted/controlled workers       | Downloads through public URLs, stable installer selection, checksums and installed version               |

Do not equate a standard macOS compile job with GPU coverage. GitHub also offers [larger macOS runners with M2 GPU acceleration](https://docs.github.com/en/actions/reference/runners/larger-runners); those can cover a bounded M2 test if available to the account, but do not establish M1/M3/M4/M5 or large-memory validation. Dedicated Macs remain the straightforward way to cover the required families and large models.

Read runner selection from repository configuration, for example `ZINC_RUNNER_METAL_APPLE7`, `ZINC_RUNNER_RDNA4`, and `ZINC_RUNNER_INTEL_XE2`. Resolve any SSH endpoint/device selector from approved environment variables. Publish no private runner names, endpoints, GPU UUIDs, serials, or host-specific paths.

GPU workers must be dedicated validation resources. The developer workstation is excluded from unattended inference under the repository's GPU placement policy. Provisioning a new worker and credentials is implementation work; planning this release does not authorize local GPU runs.

### Hardware scheduling and cleanup

Use both workflow concurrency and a host/device reservation shared across backends. A Vulkan lock and a separate HIP lock do not protect the same physical GPU from simultaneous workloads.

Each test command owns its server lifecycle: start, wait for health, exercise it, and stop the owned PID in `finally`/`trap` before returning. Run one model process at a time on a GPU. Never stop unrelated workloads. Record cleanup failure, cap job/model timeouts, and retain bounded sanitized logs. Cache models by verified digest and shader/JIT caches by the complete driver/runtime/kernel-source identity.

GPU/signing workers accept trusted main/release source only. Fork PR code stays on hosted unprivileged workers. Keep build/GPU permissions read-only; grant release writes and attestation/signing permissions only to the jobs that require them. Pin third-party actions to reviewed commit SHAs.

## 5. Hardware and model validation

### Evidence for each claimed combination

Every result binds the archive SHA256, full source SHA, backend, GPU family/model, OS, driver/runtime, model SHA256, quantization, context configuration, and test suite version. Assert that the actual GPU family matches the requested cell; reject CPU/software fallbacks such as llvmpipe. A result from a source-tree binary or older nightly cannot certify the candidate package.

Required candidate checks:

- Fresh installation and execution outside the repository, including a path containing spaces, symlinked launch, and a different working directory.
- `--version`, `--check`, catalog discovery, model pull with hash verification, and a coherent CLI/chat completion.
- Cold and warm shader/JIT initialization; deliberate missing/incompatible runtime and asset failures with actionable diagnostics.
- Tokenizer/template parity and numerical kernel checks against llama.cpp references, plus deterministic first-token/continuation checks on exact prompts and GGUFs.
- HTTP health/models, non-streaming completion, supported streaming chat, cancellation, malformed requests, context-boundary errors, and the built-in chat UI.
- A second request after errors/cancellation, repeated load/unload, and memory/fit rejection without corrupting the GPU or leaving a server behind.
- Default options and any advertised optional paths, including thinking, session/prefix reuse, model switching, tools, MTP, and concurrent slots where that backend supports them.

Required shared-memory regression shapes include 32/64 KiB cache limits and widths above the cache. Include the BOS/template regression from PR 30. Reuse `tools/validate_dmmv_shared_cache.c`, `tools/llama_parity.sh`, and existing API validation tools rather than replacing reference checks with ZINC-to-ZINC comparisons.

### Model profiles and memory

| Profile                 | Purpose                                                      | Placement                                                                       |
| ----------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| Qwen3 0.6B Q8_0, 639 MB | Basic installation, tokenizer/chat/API checks, 8 GiB systems | Every required Metal/Vulkan family; ROCm uses its supported Qwen3.5 hybrid path |
| Qwen 3.5 9B             | Hybrid attention/SSM with dense FFN                          | Devices where the measured model/context budget fits                            |
| Qwen 3.6 35B-A3B        | MoE plus SSM and mixed quantizations                         | Large-memory Metal, AMD Vulkan/ROCm, Intel Vulkan                               |
| Gemma 4 26B-A4B and 31B | Different tokenizer/template and MoE/dense execution         | Validated supported backend/device combinations with sufficient memory          |
| Qwen 3.8 27B            | Native-context and MTP coverage                              | Backend-specific claims supported by release evidence                           |

The catalog now includes an immutable, checksum-pinned Qwen3 0.6B Q8_0 starter, initially experimental with no claimed tested profiles. Qualify it on the Metal/Vulkan families before promoting its status and building the final candidate. ROCm does not implement this plain-Qwen3 path and starts with Qwen3.5 9B on its 32 GB reference worker. A hardware support claim must come with a practical model. Keep thinking off for the small starter unless output stability is demonstrated.

Do not run large-model cells on 8/16 GiB Macs or small-VRAM cards and call an OOM a GPU incompatibility. Put required jobs on workers that fit their assigned model. Publish capacity/fit results separately from correctness. An approved policy can mark a model/device combination inapplicable; the required small-model family check still must run.

The existing catalog records GPU profiles, not a complete backend/OS/driver/model matrix. Align catalog recommendations and download-page claims with backend-aware release evidence. A result for ROCm does not automatically certify Vulkan on the same AMD GPU.

Keep advertised context limits and MTP behavior specific to the validated model/backend. Test default MTP against ordinary greedy decode, rejection-state restoration, and single-/multi-slot behavior where available. Do not transfer ROCm's native-context or concurrency results to Metal/Vulkan by implication.

### Performance gate

Use the fair server-vs-server harness in `tools/performance_suite.mjs` with the same GGUF, scenarios, warmups, run counts, and server-side timings. Compare a candidate with its previous known-good ZINC build on the same device/runtime as well as recording the llama.cpp reference.

A proposed alert threshold is a repeatable 5% regression in decode/prefill or 10% in latency; establish per-profile noise and a measured baseline before using those numbers as a blocking policy. A single noisy run triggers investigation, not an automatic conclusion. Correctness and install failures always block publication. Publish only measured performance claims and label CLI/kernel diagnostics separately.

## 6. Versioning and promotion

A release-preparation PR freezes support policy, model hashes, toolchains, notes, and known limitations. The candidate workflow resolves a full SHA from trusted main and builds with the intended final version, such as `0.1.0`. Its unique identity is the version, source SHA, run ID, and archive digests. The final tag need not exist while these candidate artifacts are tested.

After all required jobs pass, the release approver reviews the actual downloadable candidate, notes, and validation summary. The publish job rechecks the approved run/workflow/source identity and every digest, then creates `v0.1.0` pointing to that SHA. It can stage a draft GitHub Release, upload the already-tested assets, verify the downloaded assets, and then publish it. Complete the staging/upload checks before changing the release to public.

The current tag-triggered workflow becomes part of this shared pipeline: external tag events verify the tag/candidate association and run publication checks rather than silently rebuilding different release bytes. Avoid recursive or duplicate release runs when the publisher creates a tag. Protect release tag creation and the publish environment.

A public `0.1.0-rc.1` is a separate pre-release with its own embedded version, assets, and results. Its binaries cannot simply be renamed into `0.1.0`. A final-version candidate is built and validated again. Within a single candidate, signing, metadata, or content changes invalidate the frozen digests and require the applicable checks again.

Published tags and assets are immutable. Re-running publication with identical candidate digests is idempotent; different bytes under an existing published version fail. A code change gets a new candidate, and a fix after publication gets a new version. Installer rollback changes the selected version, never the model cache or the contents of an existing release.

For 0.1.0, automate every build/test/sign/package step and keep one explicit publication approval. Nightlies and RCs do not become `latest`; only the approved stable version does.

## 7. Public feature contract

Generate a concise feature/model matrix for each backend from the candidate results. The release notes and website must agree with the shipped CLI and API, including:

- Which models/quantizations are supported and the practical memory/context requirements.
- CLI/chat availability, streaming behavior, tool calls, sessions, switching, and concurrency per backend.
- Existing API limits such as absent embeddings/media endpoints and raw-completion behavior.
- Runtime dependencies, tested driver versions, signing status, install/upgrade/rollback commands, and experimental paths.

The candidate now generates download names, model/context tables and hardware rows directly from validation, replacing the old TBD notes. Do not promise complete OpenAI API compatibility or production multi-tenant service operation. Single-slot release validation does not certify ROCm's broader concurrent serving implementation. Keep the initial documented serving setup local and describe the actual listening/authentication behavior.

The install page should present the three choices clearly, default appropriately, and offer a small-model first run. Move prerequisites needed only for building into the contributor path. The benchmarks page remains evidence-driven and links to the matching measurements, rather than becoming a release speed claim without a matched run.

Release engineering should add automatic jobs in reviewable PRs rather than combining them with inference changes. Keep planning, implementation, RC validation, and public publication as distinct completed outcomes.

## 9. Release exit checklist

- [ ] Approve the hardware support contract, OS floors, and per-backend feature/model policy.
- [ ] Provide every required GPU family with a trusted validation path and reserve the hardware.
- [ ] Configure Developer ID/notarization credentials and verify the chosen Mac delivery format.
- [ ] Pin Zig, Bun, shader compiler, ROCm image/runtime ABI, Xcode/SDK, and actions.
- [ ] Complete model checksums, immutable references, licenses, and the small starter.
- [ ] Build all three artifacts from one SHA with final-version metadata.
- [ ] Pass minimum/current userspace package and installer tests outside the repository.
- [ ] Pass every required artifact-based GPU, correctness, API, memory, and cleanup gate.
- [ ] Review measured performance changes and backend-specific context/MTP claims.
- [ ] Produce final digests, provenance, dependency inventory, notes, and validation results.
- [ ] Rehearse failed validation, unavailable runner, interrupted upload, duplicate version, and rollback.
- [ ] Approve and publish `v0.1.0` with the verified bytes; verify public download/install URLs.
- [ ] Close issue 10 after the public binaries and automatic release process work.

A planning PR or a green source build does not close issue 10. The user-facing result is a public release that can be downloaded, verified, installed, and exercised on the stated hardware.

For 0.1.x, maintain the published install/backend contract and make bug fixes through patch releases. Introduce intentional compatibility changes through an explicit minor-release plan, with migration notes. Reuse this pipeline rather than overwriting a published archive.
