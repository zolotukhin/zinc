# ZINC 0.1.0 release readiness

Target: `v0.1.0`. Tracking: [issue #10](https://github.com/zolotukhin/zinc/issues/10).
Release automation landed in [PR #33](https://github.com/zolotukhin/zinc/pull/33).

## Current status

As reviewed on 2026-10-26, the three CPU-only packaging jobs pass on `681931cd`:
Metal, Vulkan, and ROCm build, pass their ABI/dependency audits, and install from
an extracted archive outside the checkout. The source tests and site build also
pass. These results establish packaging behavior; they do not certify GPU
inference with the delivered archives.

There is no published binary release yet. The `release-signing` and `release`
environments now accept only `main`; publication requires maintainer review.
Apple signing credentials, GPU runner assignments, and registered release
workers are still missing. RDNA4 and Intel Xe2 developer access has been
verified, but access alone does not constitute packaged-artifact qualification.
The small starter is still experimental. Keep all nine required profiles for
the first stable release; missing hardware is not a reason to skip a profile.

## Distribution contract

The [release policy](https://github.com/zolotukhin/zinc/blob/main/config/release/targets.json)
is the source of truth for targets, OS/ABI floors, hardware profiles, model
hashes, context limits, and the reference engine revision.

| Archive suffix        | Runtime baseline                                     | Required hardware profiles          |
| --------------------- | ---------------------------------------------------- | ----------------------------------- |
| `macos-aarch64-metal` | macOS 15+, native ARM64; signed and notarized        | Apple7, Apple8, Apple9, Apple10     |
| `linux-x86_64-vulkan` | glibc 2.35+, Vulkan 1.3 driver                       | RDNA3, RDNA4, Strix Halo, Intel Xe2 |
| `linux-x86_64-rocm`   | glibc 2.39+, ROCm 7.2.4 and runtime compiler headers | RDNA4 `gfx1201`                     |

Metal and Vulkan include browser chat. ROCm provides CLI/HTTP chat without the
built-in UI or hot model switching. CUDA remains experimental and source-only.
Models and GPU drivers are separate installations.

Required hardware that is unavailable blocks that support claim. Changing the
launch matrix is an explicit policy change; an omitted or skipped profile does
not count as a pass. Historical source-build benchmarks and OpenCode trials
remain useful evidence, but cannot certify a different packaged executable.

## Implemented

- Frozen source SHA/version and baseline CPU/OS targets for all three archives.
- Complete shader inventories, dependency/ABI audits, normalized archive metadata,
  per-file checksums, and executable identity probes.
- Verified user-local installation, atomic activation, backend selection, safe
  reinstall, failure handling, and rollback without moving models.
- Separate untrusted packaging, trusted candidate, signing, hardware validation,
  provenance, protected promotion, and public-install workflows.
- Packaged-byte GPU/model/API/reference checks, process cleanup, generated
  validation tables, and resumable publication that refuses replacement bytes.

See [release engineering](https://zolotukhin.ai/zinc/docs/releasing/) for the
maintained commands and configuration, and [binary installation](https://zolotukhin.ai/zinc/docs/binary-releases/)
for the user-facing contract. This readiness note replaces the original design
proposal; implementation details belong in those guides and the policy.

## Remaining launch gates

1. Configure the eight runner roles covering nine hardware profiles. Reserve
   shared GPUs and install each worker's private model/reference configuration.
2. Configure Developer ID signing/notarization credentials in `release-signing`.
   The main-branch restrictions and required publication reviewer are configured.
3. Run an RC from one frozen SHA. Review all packaged-artifact reports, exact
   model hashes, correctness/API checks, and process cleanup.
4. Qualify and promote the small starter in the catalog from real hardware
   evidence. Keep optional KV/MTP/context/concurrency claims within their tested
   scope; review performance regressions separately.
5. Rehearse failed validation, unavailable workers, interrupted upload, duplicate
   versions, and rollback. Build a new final-version candidate after source changes.
6. Publish the approved candidate unchanged. Verify public downloads and clean
   installation before closing issue #10.

No release tag or public archive should be created from the packaging preview.
