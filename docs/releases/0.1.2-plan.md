# ZINC 0.1.2 candidate

[0.1.1 is published](https://github.com/zolotukhin/zinc/releases/tag/v0.1.1).
0.1.2 is the next Linux maintenance candidate. The chat, MTP controls and native
model lifecycle changes on main need qualification in final-version archives
before they become part of the stable binary support promise.

## Scope

- AMD Radeon AI PRO R9700: HIP / ROCm first; Vulkan remains an explicit alternative.
- Intel Xe2: Vulkan, with the existing seven pinned models.
- Retain six ROCm model pins, their native reference gates and the selected
  release-policy contexts. A larger interactive context is separate evidence.
- Metal remains an unsigned preview. CUDA and native Intel remain experimental.
- Include the [0.1.2 changes](0.1.2-changes.md).

## Lifecycle stability gate

Every Linux hardware profile must run the installed archive through all its
pinned models in one owned server. Qualification requires one complete warm-up
round followed by three measured rounds at 4K context and one request slot.
Each model exercises activation, queued JSON requests, streaming, transport
cancellation, recovery, rejected activation and unload without deleting weights.
Native per-request MTP controls additionally exercise queued on/off isolation.

Sample the same unloaded state after each round. Keep distinct counters for
process RSS, DRM resident VRAM, DRM resident host memory and open descriptors.
Deduplicate duplicated DRM descriptors by client/device internally; reports
contain only totals, model IDs and immutable artifact identities.

The maximum growth above the post-warm-up baseline is 128 MiB RSS, 64 MiB VRAM,
128 MiB GPU host memory and zero descriptors. These are bounded regression
budgets, not a promise of unlimited uptime. The aggregator recomputes growth
from every sample and rejects incomplete rounds, changed settings, wrong model
sizes, another binary, missing telemetry or unsuccessful cleanup.

`tools/run_model_lifecycle_soak.py` provides a longer development run (eight
measured rounds after two warm-up rounds by default). Run it only on the remote
Linux GPU node. Give `--config` a private file outside the checkout containing
an installed binary, backend, selected device, context and verified model paths;
`--output` receives sanitized JSON. `--private-log` optionally preserves server
logs locally. The runner owns and stops its child and uses an isolated cache
namespace of links; it does not download, copy or delete the original weights.

## Remaining qualification

1. Keep post-merge CI, privacy, site and package checks green.
2. Run the longer R9700 soak, including both AMD backends. Preserve failed
   attempts and fix regressions with tests before freezing a candidate.
3. Build Vulkan and ROCm archives once, embedding 0.1.2 and a frozen main SHA.
4. Run all 20 model/backend rows, numerical/native reference checks, context
   boundaries, cancellation and the new lifecycle gate on those exact archives.
5. Exercise actual OpenCode/OpenClaw tasks, including Intel where supported.
   Preserve unsupported-model limits and independent acceptance failures.
6. Rehearse 0.1.1-to-candidate installation, rollback, reinstall, command links
   and model-cache preservation in isolated prefixes.
7. Verify checksums, provenance, every hardware report and release notes before
   protected publication. An unavailable or failed Intel profile blocks stable
   certification; AMD evidence cannot replace it.
8. Update the website's stable version and feature claims after publication.

The prior development tests established six HIP models, browser behavior, MTP
request isolation and real allocation-failure recovery. They do not certify the
future archives. Release publication uses the existing protected workflow and
promotes qualified bytes without rebuilding them.
