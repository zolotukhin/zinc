# ZINC 0.1.2 candidate

[0.1.1 is published](https://github.com/zolotukhin/zinc/releases/tag/v0.1.1).
0.1.2 is the next Linux maintenance candidate. The chat, MTP controls and native
model lifecycle changes on main need qualification in final-version archives
before they become part of the stable binary support promise.

## Scope

- AMD Radeon AI PRO R9700: HIP / ROCm first; Vulkan remains an explicit alternative.
- Intel Xe2: Vulkan, with the existing seven pinned models.
- Retain six ROCm model pins, their native reference gates and the selected
  release-policy contexts. A larger interactive context is separate evidence.
- Metal remains an unsigned preview. CUDA and native Intel remain experimental.
- Include the [0.1.2 changes](0.1.2-changes.md).

## Lifecycle stability gate

Every Linux hardware profile must run the installed archive through all its
pinned models in one owned server. Qualification requires one complete warm-up
round followed by three measured rounds at 4K context and one request slot.
Each model exercises replacement of resident weights, activation, queued JSON
requests, streaming, transport cancellation, recovery, rejected activation and
unload without deleting weights.
Native per-request MTP controls additionally exercise queued on/off isolation.
The candidate repeats its three frozen native reference continuations after
every activation/cancellation sequence; certification rejects missing cases.

Sample the same unloaded state after each round. Keep distinct counters for
process RSS, DRM resident VRAM, DRM resident host memory and open descriptors.
Deduplicate duplicated DRM descriptors by client/device internally; reports
contain only totals, model IDs and immutable artifact identities.

The maximum growth above the post-warm-up baseline is 128 MiB RSS, 64 MiB VRAM,
128 MiB GPU host memory and zero descriptors. These are bounded regression
budgets, not a promise of unlimited uptime. The aggregator recomputes growth
from every sample and rejects incomplete rounds, changed settings, wrong model
sizes, another binary, missing telemetry or unsuccessful cleanup.

The 32 GB R9700 native profile also requires two real allocation-failure probes:
27B at 64K context attempting to switch to Gemma 31B, and 9B at 262K attempting
to switch to 27B. Each must reach a failed model load, restore the original
model and reproduce its greedy continuation. A rejected request before loading
does not qualify. These contexts are failure controls, not expanded model
support claims. The report binds both probes to the same candidate binary and
requires successful process cleanup.

`tools/run_model_lifecycle_soak.py` provides a longer development run (eight
measured rounds after two warm-up rounds by default). Run it only on the remote
Linux GPU node. Give `--config` a private file outside the checkout containing
an installed binary, backend, selected device, context and verified model paths;
`--output` receives sanitized JSON. `--private-log` optionally preserves server
logs locally. The runner owns and stops its child and uses an isolated cache
namespace of links; it does not download, copy or delete the original weights.

The [R9700 development evidence](https://zolotukhin.ai/zinc/validation/model-lifecycle-development-2026-11-18.json)
retains the failed Vulkan run and the cleanup fix: the same 63 operations and
54 resident swaps changed VRAM growth from 1,280 MiB to zero. The fixed run's
maximum RSS growth was 61 MiB. Native HIP passed 24 operations, 20 resident swaps
and both real failed-load recovery probes, with 1.4 MiB maximum VRAM growth and
no RSS or descriptor growth. These standalone development runs contain no
repeated frozen-reference cases; they cannot certify a final archive.

The later idle-heap development runs in the
[November 19 record](https://zolotukhin.ai/zinc/validation/release-candidate-0.1.2-amd-2026-11-19.json)
used eight measured rounds after one warm-up. Vulkan passed 63 operations and
189 repeated references with 64.7 MiB peak RSS growth; HIP passed 54 operations
and 162 references with 71.7 MiB. GPU host memory and descriptors stayed flat.
These development binaries use glibc 2.39 and do not certify the final archives.
The separate Linux CPU contract returns a touched 64 MiB region while preserving
a live allocation; disabling the production reclaimer makes it fail.

## Remaining qualification

1. Keep source CI, privacy and site checks green. The AMD archive, installer and
   actual-client preparation above has passed. Prepare another cut if release
   qualification inputs change; retain the dated records and their failures.
2. Qualify fresh packages after the Vulkan replacement repair. Rerun both AMD
   profiles and the Intel model, reference, cancellation and lifecycle checks
   before certifying the new candidate.
3. Repeat actual Intel OpenCode/OpenClaw acceptance at the documented contexts,
   retaining starter limitations, failed trials and independent verification.
4. Aggregate all three required profiles, verify checksums, offline provenance
   and release notes, then use protected publication. AMD evidence cannot
   replace the Intel profile.
5. Complete public-download/install checks and update stable website version
   and feature claims only after publication.

Release publication promotes the qualified bytes without rebuilding them.
Neither the preparation snapshot nor the earlier standalone development runs
can replace a complete three-profile release certificate.
